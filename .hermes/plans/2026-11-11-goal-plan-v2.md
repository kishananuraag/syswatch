## 3. The progress cockpit — "open syswatch and see the work happening"

First-class deliverable. syswatch becomes the place you watch agents work, not this chat.

```
driver.py ──writes──▶ .hermes/run/events.jsonl ──served──▶ GET /api/agent-stream (SSE)
                                                                    │
                                              syswatch dashboard ◀──┘
```

Event contract:
```json
{"ts":"...","job":"T5","kind":"brief|dispatch|stdout|verify|retry|pass|fail|checkpoint",
 "model":"...","attempt":2,"text":"...","exit":0,"duration_s":412}
```

**Panes, built to read like a chat because that's how you read work:**
1. **GOAL** — your words, fixed, with `n/N acceptance passing` live
2. **ME (Chief of Staff)** — my briefs and my verdicts, input/output blocks exactly like this chat
3. **WORKER** — current agent: model, attempt, elapsed, streaming stdout tail
4. **QUEUE** — backlog chips: queued / running / verifying / failed / done
5. **LEDGER** — last 50 attempts, one row each, click through to the raw log

**Rules:** no claim without a ledger row behind it; green only when an acceptance command exited 0; failures stay visible.

## 5. The loop (auto-evolving until the goal is met)

1. Read `GOAL.md` + `BRAIN.md` + last 20 `LEDGER.jsonl` rows
2. Pick next task (dependency-ordered, smallest verifiable slice)
3. Write `briefs/<job>.md` — goal · file paths · constraints · **acceptance commands** · "do not claim success; report commands and output"
4. Dispatch in a **git worktree**, log to `logs/<job>-<attempt>.log`, emit events
5. **Verify myself** — acceptance commands only
6. Routing: attempt 1 → same model + failing output pasted back · attempt 2 → rotate model · attempt 3 → **stop retrying, re-plan the task** · attempt 4 → checkpoint to you
7. Append `LEDGER.jsonl`, update `BRAIN.md`, emit verdict
8. Repeat until every acceptance command passes or a stop condition fires

**Stop:** goal met · three consecutive no-progress iterations · a decision only you can make · daily paid budget hit.

## 8. Operating hours — the unattended chain (added 2026-11-11)

**Rule: I do not supervise during your peak hours. From 11:30 IST I go quiet.**

What that changes mechanically — verification has to survive without me:

| Concern | Unattended answer |
|---|---|
| Who verifies? | The **driver**, using deterministic acceptance only: exit codes, JSON schema validation, numeric thresholds, file-exists checks. No opinions. |
| What about judgement calls? | They get **parked**, not guessed. Status `needs_review` in the ledger with the log attached. I clear that bucket when I'm back, never mid-peak. |
| Do tasks stop when one fails? | No. The queue is dependency-ordered: a failed task blocks only its dependents; independent tasks continue. Failures accumulate in the report. |
| How do you know what happened? | One `reports/<date>.md`: tasks done, tasks failed + failure signature, before/after numbers (CPU, RSS, binary size), and anything needing your decision. Two-minute read. |
| Token burn | My spend becomes **O(batches planned)**, not **O(iterations supervised)**. Agents are $0 regardless of how many run. |

**The driver contract:** `queue.json` in, `LEDGER.jsonl` + `reports/<date>.md` out, zero paid tokens in between. If the machine dies mid-run, the ledger shows exactly which task was in flight and which worktree to inspect.

**Resume protocol:** I read the report, verify the `pass` claims myself with the acceptance commands (trust the ledger only after re-running the checks), then plan the next batch. Never "continue from where it stopped" without re-proving the last green.

## 9. Thermal and load discipline (added 2026-11-11 — this is your 90 °C)

Observed: one `cargo build --release` pinned all 8 cores and took the machine to **90 °C**. Unacceptable when you're working on the same box.

Rules baked into the driver and every brief:

1. **One build-heavy task at a time.** Parallelism is for non-compiling work only.
2. **`CARGO_BUILD_JOBS=4`** for agents — half the cores, roughly double the wall time, a fraction of the heat.
3. **`cargo check` first, `cargo build --release` only when the acceptance command needs the binary.** `check` is ~3× cheaper and catches most agent mistakes.
4. **`nice -n 10`** on every agent build so your foreground work always wins.
5. **Pre-flight guard in the driver:** before launching a build, sample load and thermal state; if load > 50 % or temp > 85 °C, sleep 60 s and re-check instead of firing.
6. **Benchmarks run alone**, after builds, never concurrently with anything (otherwise the numbers are garbage anyway).
7. Report thermal peak alongside CPU/RSS in every measurement — an optimization that halves CPU but doubles temperature hasn't won.
