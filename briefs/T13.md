## Work items

1. **Wire every chart.** On load, each overview card fetches
   `/api/graph?metric=<m>&range=<r>` and feeds the Chart instance (points use
   `ticks` labels from the ladder). Cards: cpu, memory, gpu, network, disk,
   power. Section pages too. A chart with no instance must get one.
2. **Refresh loop.** `setInterval` two cadences: `/api/current` + KPI numbers
   every 1 s; `/api/graph` every 5 s. Range switch re-fetches immediately.
   Guard against overlapping fetches (in-flight flag).
3. **Power history with timeframes.** New endpoint `/api/power/history`:
   the dashboard samples `battery_w` + total W + biggest app every 5 s into an
   in-memory ring (1 s → 15 min, 5 s → 6 h, 60 s → 24 h, cascade keeping
   max+mean — same shape as the collector's). Power card + power section show:
   **current W (1 s), and W over 1 m/1 h/1 d/7 d** using that ring; the graph
   must populate and tick-refresh. Honest nulls when the ring is still filling
   (`available_from_s`).
4. **Analytics page** (`/analytics`, linked from nav). Machine-usage analytics
   from the existing endpoints, computed server-side (`/api/analytics`):
   - window averages and peaks for cpu / memory / network rx-tx (per range)
   - busiest hour of the last 24 h (cpu)
   - top 10 apps by CPU right now and by energy (collector `by_energy`)
   - network totals: GB sent/received today (integrate the rate series)
   - uptime + load averages + process count trend
   Every number must come from measured series — no invented values; where a
   series is missing (e.g. disk), render `unavailable` + reason.
5. **GPU/Disk honesty.** Live `/api/current` lacks gpu and disk activity —
   check whether the collector JSONL (SYSWATCH_LOGS) already carries them; if
   it does, serve them; if it does not, keep the `unavailable` + reason cards
   ("collector does not sample GPU utilisation") and do NOT fake numbers.
   Do not modify `src/` in this round.
6. Keep: no CDN, no build step, chart.umd.min.js stays vendored.
