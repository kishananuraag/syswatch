# T14B — Sensor registry, temperatures, E/P cores, power timeline, Power BI model

Master spec: `briefs/T14.md` addenda 1–3 + `docs/machine-capability-inventory.md`
+ `docs/ui-design-system.md` (Parts 1 & 2). T14A ships the shell and working
charts; this round goes deep on sensors and analysis.

## 1. Sensor registry (`dashboard/sensors.py`)

Adapter interface per the inventory doc; `MacOSAdapter` implemented, Windows /
Linux stubs returning `platform: "unsupported yet"`. `/api/sensors` returns
`{id, group, label, value, unit, available, reason, source, precision}` per
sensor. UI renders groups dynamically; a group with zero sensors does not
render, except a single amber "needs root" row when that is the reason.

## 2. Temperatures (root-gated, honest)

Consume the T15 privileged daemon file when present: CPU die, per-cluster,
GPU, SSD (if exposed), battery (also readable unprivileged when the key
exists), thermal pressure, fans. Not granted → one amber row
`Temperatures — needs root` with a Grant link. **Never a placeholder 0 °C.**

## 3. E/P cores

Per-cluster rings/bars plus per-core rows discovered from
`hw.perflevel0/1.logicalcpu` (4 P + 4 E here), each with utilisation and temp
when available. Labels from the platform.

## 4. Power timeline + what is being calculated (user's explicit ask)

> "the power metrics, it should be by timeline as well. user don't know how
> long it is being calculating. also on battery or power it has drawn and
> charging port wattage. everything that could be analysed."

- **Power over time:** `/api/power/history` already returns a ring. Expose it
  per range (`?range=1h|6h|1d|7d`) and chart: **battery draw W**, **adapter
  input W** (when connected), **package W** (when root granted). Series on one
  axis, distinct line styles, never stacked.
- **Coverage/disclosure line under every power visual:**
  `sampling every 5 s · 78 samples · since 03:32 (36 min)` — the user must
  always know the window behind the number. Derive from the ring's
  `oldest_ts`/`newest_ts`/`sampling_s`.
- **Draw vs charging-port wattage:** battery `drawn_w` = |V×A| (unprivileged,
  verified 4.19 W live). `adapter_w` from ioreg `AppleRawAdapterDetails` —
  available only while connected (verified empty on battery:
  `ExternalConnected=No`); UI shows `on battery` otherwise. When both exist,
  show **charging efficiency** = drawn ÷ adapter input as a secondary stat,
  labelled as an estimate.
- **Everything analysable, at minimum:** energy over window (Wh, ∫W dt),
  cost estimate only if the user configures a tariff (default: hidden),
  per-app Wh share over the window, peak draw + time, average draw, battery
  drain rate %/h, projected empty time, cycles since window start.

## 5. Power BI interaction model

Per `briefs/T14.md` addendum 2 §G: cross-filter (click app row / core / spike
→ filters other visuals), filter chips, drill-through to entity detail
drawer. Analytics page = the model page: slicers (time, group, app), measures
table (avg/max/p95/Δ vs previous window/coverage), findings block (3–4
sentences computed from real series), records feed (`03:12 · CPU peaked 91 %
— Chrome Helper`).
