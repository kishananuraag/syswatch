# T15 — Permissions panel + root power tier (user-approved)

The user has GOED the root tier: "we go root and it should ask for necessary
permissions, and the dashboard should also show if there are untoggled
permissions that are required."

Read `docs/ui-analytics-plan.md` tier model. This brief implements Tier 3
properly plus a permissions surface. SECURITY RULES are hard:

- The dashboard HTTP server NEVER runs as root and NEVER gains root by
  holding a password. Root is granted ONLY through a macOS admin prompt
  (osascript `with administrator privileges`) that THE USER approves.
- The root component is a LaunchDaemon running
  `/usr/sbin/powermetrics -f <file> -i 5` (interval 5 s, one sample per file
  rotation) writing to
  `~/Library/Application Support/syswatch/root/powermetrics.json` (or .txt).
  The unprivileged dashboard only READS that file.
- No password is ever stored, echoed, logged or printed. Any code that
  captures the password is a defect. The osascript prompt hands the
  credential straight to the privileged helper action and discards it.

## Work items

1. **`/api/permissions`** — returns the honest state of every privilege the
   system uses and what it unlocks:
   - `package_power`: probe = does the root powermetrics file exist AND is it
     newer than 30 s? unlock text: "CPU/GPU package watts".
   - `assistive_access`: probe = run a harmless `osascript` AX read on our own
     process; -1719 → not granted. unlock text: "menu-bar AX diagnostics".
   - `battery_stats`: always true (unprivileged ioreg) — listed as "granted"
     so the panel is complete.
   Each entry: `{id, granted, unlock_text, how_to_grant}`.
2. **Grant flow (one click, one prompt).** `POST /api/permissions/grant?id=package_power`
   → runs the single osascript that installs the root LaunchDaemon via
   `launchctl` under `with administrator privileges`:
   - writes `packaging/launchd/com.barbarian.syswatch.power.plist` (template
     with `__HOME__` already exists for agents; add the daemon template)
   - `launchctl bootstrap system /Library/LaunchDaemons/...` inside the
     privileged osascript action (a `do shell script ... with administrator
     privileges` one-liner).
   Idempotent: if already granted (file fresh + daemon loaded), return 200
   without prompting. A decline returns `granted:false, reason:"user declined"`.
   **Never** auto-run at page load or in any poll — only on explicit button.
3. **Permissions panel** (nav tab, contract styling): rows per permission —
   name, granted (semantic green dot) / not granted (amber dot), what it
   unlocks, and a single "Grant" button only for the not-granted ones.
   Header text explains the root model in one sentence.
4. **Power page upgrade.** When `package_power` is granted: CPU/GPU package
   watts from the root file appear in the power KPI, the power chart, and the
   analytics aggregates, replacing the nulls. Label the source. When the file
   goes stale > 30 s, fall back to null + reason — never a cached number
   presented as live.
5. **LaunchDaemon plist template** in `packaging/launchd/`:
   `com.barbarian.syswatch.power.plist` with `__HOME__` placeholder, RunAtLoad,
   KeepAlive, powermetrics args `-i 5 --sample-rate 5 -f <file>` (verify
   actual flags against `powermetrics --help` in the sandbox and use what
   works; document the real flags in the file header comment).
   Extend `packaging/launchd/install.sh` NOTES (not the T8 install path) with
   the daemon install snippet used by the grant flow.
6. Uninstall path: a "Revoke" button = same prompt pattern running
   `launchctl bootout system /Library/LaunchDaemons/...` + delete file.

## Honesty rules

- `powermetrics` fields parsed for real: `CPU Power`, `GPU Power`,
  `Package Power` (mW). Missing field → null + reason, never 0.
- If the admin prompt is denied, the panel row stays amber and the power page
  keeps saying "needs root".

# ADDENDUM — the privileged daemon also carries temperatures, fans, and Neural Engine

Because `powermetrics` is root-only (verified: "powermetrics must be invoked as
the superuser") and unprivileged macOS exposes no named temp sensors, the
daemon's output is the platform's temperature source. Extend item 5:

- Daemon command samplers: `--samplers thermal,smc,gpu_power,cpu_power`.
  Emit ONE JSON snapshot per sample to
  `~/Library/Application Support/syswatch/root/sample.json`:
  ```
  { "ts": ..., "cpu_temp_c": ..., "gpu_temp_c": ..., "cpu_cluster_temps_c": [..],
    "package_w": ..., "cpu_w": ..., "gpu_w": ..., "ane_w": ...,
    "thermal_pressure": "Nominal|Moderate|Heavy|Trapping|Critical",
    "fans_rpm": [...], "ane_util_pct": ... }
  ```
  Parse the real lines `CPU die temperature:`, `GPU die temperature:`,
  `Combined Power (CPU + GPU + ANE):` and friends — dump one real sample in
  the log as evidence of the exact field names on this macOS version.
- Missing fields → key omitted (not 0). Dashboard turns omissions into
  `unavailable` + reason.
- `/api/permissions` gains `temperatures` and `neural_engine` rows whose
  granted state is the same root grant (one permission unlocks all root-tier
  sensors; present it as `Elevated sensors (temperatures, package power,
  Neural Engine)`).
