# T14C — P/E mapping fix, per-module consumption, range-based Apps

Supervisor-verified defects. Fix these; touch nothing else.

## 1. Performance / Efficiency cores ARE SWAPPED (confirmed empirically)

Evidence: a single busy thread (one core) sampled through `/api/current` three
times showed spikes at indices 4, 6 and 4 (53 %, 73 %, 82 %) while indices 0–3
stayed near 30 %. On Apple Silicon the **efficiency cluster is enumerated
first**: logical CPUs 0..(E−1) = Efficiency, the next P = Performance.

- `hw.perflevel0.name = Performance`, `hw.perflevel1.name = Efficiency`
  (verified), but perflevel numbering does NOT map to core index order.
- Correct mapping: `cores[0 .. perflevel1.logicalcpu-1]` → **Efficiency**,
  `cores[perflevel1.logicalcpu ..]` → **Performance**.
- The `clusters` array in `/api/current` must list them in index order with
  correct names: `[{index:0..3, name:"efficiency"}, {index:4..7, name:"performance"}]`.
- UI labels, rings and per-core rows must follow the array — no hardcoded
  "first N = performance" anywhere. Add a comment with the evidence above.

## 2. Kill "gap to leader"

User: *"apps - gap to leader? tf you think is this a race?"* — the F1 metaphor
is rejected. Replace with **share of total**: `Chrome 0.46 W · 38 % of total`.
No gaps, no positions, no leaderboard metaphors. Same for any other sports
framing in the UI.

## 3. Every module shows WHO is consuming — full list, for the selected range

Not live-only, and **not a top 5**. Under each module's chart (CPU, GPU, Disk,
Network, Power, Memory) add a **Consumers** panel: every process that
consumed measurably in the selected range, ranked, in a fixed-height
scrollable tile (sticky header row, ~360 px tall, scrolls with the trackpad /
wheel). No truncation to N rows.

- Server: `/api/consumers?module=<m>&range=<r>` returns the **full** ranked
  list for the window (one row per process, with that module's metric:
  CPU % avg/max, GPU share when attributable, disk B/s, network B/s, energy
  Wh, memory MB) plus `{count, range, window_start, window_end, aggregation}`.
  If the list is genuinely huge, paginate with `offset/limit` — never silently
  drop the tail.
- Client: **virtualised rows** — only the visible window plus a small buffer
  exists in the DOM (≈30 rows), swapped on scroll via `requestAnimationFrame`.
  This is what keeps the page under the < 1 % CPU budget with 400 processes;
  do not render 400 rows and do not animate them.
- Column sort (click header), name filter (input), and row click →
  drill-through drawer with that process's own series for the range.
- Aggregation and window stated in the panel footer, same as charts.

## 4. Apps is a RANGE view, not a live feed

User: *"apps module could be also for timeline. there is no need for live
updates. it could be ranged from time to back."* — Apps renders the selected
range: sortable table (app, avg CPU, peak CPU, memory, energy Wh, disk read/
write, network) with a per-app series available on row click (drill-through
drawer). No 1 s polling on this view; it refreshes only on range change.
Live data lives on Overview/module pages, where it belongs.
