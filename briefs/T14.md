# T14 — Shell redesign: one page, persistent tabs, calm-instrument visual system

Read `docs/ui-design-system.md` FIRST — it is the design contract with exact
tokens, layout and anti-patterns. This brief implements it on top of T13's
refresh/charts/power/analytics endpoints (which must keep working).

## Work items

1. **Persistent shell.** The page is ONE document. Nav is one row of in-page
   tabs (Overview, CPU, Memory, GPU, Disk, Network, Battery, Apps, Power,
   Analytics) in the shell header. Tab click = crossfade view in place
   (opacity/transform only), never a page change. URL hash syncs (`#cpu`);
   `hashchange` renders without reload.
2. **Shared time-range control in the shell header** (1m…1y). It applies to
   the current view's charts; per-card range dropdowns are REMOVED. Changing
   view keeps range; changing range re-fetches that view only.
3. **Live badge.** `live●` in header: accent-colored + soft pulse while the
   1 s /api/current poll succeeds; on failure or 5 s of no update, dim with
   `stale Ns` label.
4. **Tokens + typography.** CSS custom properties exactly per the contract
   table (base #121317, surface #181A1F, elevated #1E2127, border #2A2E36,
   text #F4F5F8/#9BA3AE, accent #4D9FFF, semantic #5FB97A/#E3B341/#E5484D).
   Tabular numerals on all numbers. No shadows for elevation — lightness
   steps. No gradients, no backdrop-blur, no side-stripes, no second font.
5. **Overview grid rebuild.** 6 equal cards, strict 12 px gutters, Z-pattern
   order (CPU, memory, GPU, network, disk, power). Card anatomy: micro-label,
   big tabular numeral, sparkline (accent, soft area fill, subtle gridlines),
   peak chip (from /api/graph peak fields). Whole card clickable → opens that
   tab in place. Hover lift to elevated token.
6. **Section views.** Same header rhythm each: title, big current value,
   chart, stat rows (label left / tabular numeral right, hairline separators).
   Apps section: ranked table with energy column and bar-in-row.
   Analytics: narrative order per contract (day chart → avg/peaks → busiest
   hour → top apps → network totals).
7. Keep every T13 behavior: 1 s KPI poll, 5 s chart poll, in-flight guards,
   power history ring, analytics endpoint.
8. **Part 2 components** (see `docs/ui-design-system.md` Part 2): hero values
   carry attribution (`4.37 W · Chrome Helper, now`); every card carries a
   delta chip with an explicit baseline (`+1.2 W vs prev 1h`); Apps table gets
   a gap-to-leader column; every chart footer shows coverage (`day sampled
   97 %`); Analytics opens with a **findings block of 3–4 sentences computed
   from the real series** (averages, peak + time, driver app), then the
   records feed (`03:12 · CPU peaked 91 % — Chrome Helper`). Continuous
   metrics show mean/median/p95/min/max, never binned counts.

## User-reported defects (must be fixed in this round)

9. **Battery card hero = time remaining, not percent.** `5:57 remaining`
   large, `61 %` secondary, charging state chip. Source: ioreg
   `AvgTimeToEmpty` / `AvgTimeToFull` (minutes; 65535 = unknown). Unknown →
   `estimating…`, never a guessed number.
10. **ONE global timeframe control only.** Per-card/per-section range buttons
    are removed everywhere — the shell header control is the single source of
    truth. (This is already item 2; it is a known defect that per-card ranges
    still render.)
11. **GPU / disk / battery charts must populate.** All three are readable
    unprivileged — sample them dashboard-side every 5 s (no `src/` changes):
    - **GPU**: `/usr/sbin/ioreg -r -d 1 -w0 -c IOAccelerator` →
      `PerformanceStatistics["Device Utilization %"]` (also Renderer/Tiler).
      Serve as `gpu.util_pct`; the ring keeps max+mean per bucket.
    - **Disk**: `/usr/sbin/ioreg -r -d 1 -w0 -c IOBlockStorageDriver` →
      `Statistics["Bytes (Read)"]` / `["Bytes (Write)"]` are CUMULATIVE —
      differentiate over the sample interval to get B/s. Never serve the
      cumulative counter as a rate.
    - **Battery**: the existing power ring gains `pct` and
      `time_remaining_s` so the battery chart plots %/remaining over the
      selected range.
    Failure of any probe → `unavailable` + reason on that card (honest), but
    these probes work on this machine — verified by the supervisor.

## A. SENSOR REGISTRY, not hardcoded cards

Replace hardcoded metric plumbing with a **capability registry**:

- `dashboard/sensors.py`: an adapter interface `probe() -> list[Sensor]` where
  `Sensor = {id, group, label, value, unit, available, reason, source,
  precision}`. Groups: `cpu`, `gpu`, `memory`, `storage`, `network`,
  `battery`, `thermal`, `power_rails`, `clocks`.
- Implement `MacOSAdapter` NOW (ioreg, sysctl, iokit, plus reading the
  privileged sample file from T15 when present).
- Stub `WindowsAdapter` / `LinuxAdapter` with the same interface and a
  `platform: "unsupported yet"` capability row — the registry is the shape,
  not a Mac-only assumption. Adding a platform later = one adapter file.
- `/api/sensors` returns the discovered catalogue; the UI renders **groups
  dynamically**. A group with no sensors on this device simply does not
  render (plus a single Permissions/Diagnostics note explaining why).
- Per-core entries are discovered, not assumed: enumerate cores from
  `sysctl hw.perflevel0.logicalcpu` / `hw.perflevel1.logicalcpu` (Apple) and
  emit `CPU Performance Core 1..N` / `CPU Efficiency Core 1..N` rows. Same
  pattern for GPU islands and memory.

## B. Temperatures (iStat parity, permission-gated honestly)

Unprivileged macOS exposes no named temperature sensors (verified:
`ioreg` shows only `TemperatureSamples`; `powermetrics` refuses without
root). Therefore:

- Temperature rows come from the **T15 privileged daemon** sample file
  (`powermetrics --samplers thermal,smc,gpu_power`), parsed into `thermal`
  group sensors: CPU die, CPU clusters (E/P), GPU, package, SSD (if present),
  battery (ioreg unprivileged already gives battery temp if key present),
  thermal pressure (`Nominal/Moderate/Heavy/Trapping/Critical`).
- Until granted, the thermal group renders a single amber row:
  `Temperatures — needs root` with the Grant link to the Permissions tab.
  Never a placeholder number, never 0 °C.
- Sensor names stay `Sensor <n>` only when the platform gives no name; on
  macOS read real names from the thermal sampler rather than inventing them.

## C. Disk: speeds, not a usage graph

Remove the disk *usage/space* graph. Disk section shows **read and write
speed** as the charted series (derived from cumulative ioreg byte counters,
differentiated per interval), with free space as a plain hero number and
per-volume rows in the table. No space-over-time chart.

## D. GPU section: utilisation, memory, frequency, Neural Engine

GPU group includes `util_pct` (IOAccelerator `Device Utilization %`),
`renderer_util_pct`, `tiler_util_pct`, GPU frequency (existing), GPU memory in
use, and a **Neural Engine** row (`ANEMetrics` via the privileged daemon; show
`needs root` until granted). Never fabricate NE utilisation.

# ADDENDUM 2 — pressure gauges, E/P cores, and Power BI interaction model

Read `docs/machine-capability-inventory.md` — it is the capability contract.
Every group the registry reports comes from that table with its real source.

## E. Pressure first (iStat parity)

Overview gains three pressure gauges alongside the KPI cards:
- **CPU pressure** — derived from load-per-core and scheduler stall proxy;
  label the derivation in a tooltip. Never invent Apple's internal number.
- **Memory pressure** — `kern.memorystatus_vm_pressure_level` (verified live:
  value 1) mapped to Normal/Warning/Critical + % from `memory_pressure`.
- **Storage pressure** — free-ratio based, same thresholds iStat implies
  (<10 % free = critical, <25 % = warning).
A pressure gauge that cannot be derived renders `unavailable` + reason.

## F. Performance vs Efficiency cores

CPU section must show the P/E split explicitly: per-cluster utilisation rings
or bars, per-core rows discovered from `hw.perflevel0/1.logicalcpu` (this box:
4 P + 4 E, verified), each with utilisation and temperature when the root
daemon supplies it. Cluster labels come from the platform, not hardcoded.

## G. Power BI interaction semantics

- **Cross-filter**: clicking an app row, core row, spike, or chart segment
  filters the other visuals in that view; active filters render as removable
  chips under the header. Click empty space to clear.
- **Drill-through**: card → section; row → detail drawer with that entity's
  own series (app detail: cpu + energy + disk over the selected range).
- **Measures**: every view's stat rows show avg, max, p95, and Δ vs the
  previous equal-length window — computed server-side in `/api/analytics`,
  not in the browser.
- Analytics is the "model" page: slicers (time, group, app), measures table,
  and charts that respond to filters. No invented data: a measure over an
  unavailable series reports `unavailable`.
