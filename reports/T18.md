`links=2` and the matching inodes are the point: the log root carries one

`os.listdir`. Same bytes, one inode, `du` counts once.

## The cascade does not change the numbers

Same 6000 samples, read twice: once as raw 1 s lines, once as the 400 15 s
records the cascade wrote.

```
metric      layout        n            mean             min             max
cpu total   raw 1s       6000       20.5791          3.6341         57.4433
cpu total   15 s          400       20.5799          3.6340         57.4430
            delta                    0.0008          0.0001          0.0003

mem pct     raw 1s       6000       69.2479         64.7123         77.6974
mem pct     15 s          400       69.2477         64.7120         77.6970
            delta                    0.0002          0.0003          0.0004

net rx_bps  raw 1s       6000     69747.0826           0.0    19157762.19
net rx_bps  15 s          400     69745.8165           0.0    19249882.31
            delta                    1.2661           0.0       92120.12
```

The 0.000x deltas are the 3-decimal rounding in the JSON. The `net` max is
92 k high out of 19 M (0.48%) because a bucket's peak is the sum of
per-interface peaks — an upper bound inherent to storing per-interface stats.
The first implementation was 7.7% **high on the mean** because interfaces that
flapped were averaged only over the samples where they existed; absent now
counts as zero throughput, and the mean matches to 0.002%.

## Safety checks actually exercised

- raw prune compacts into `tier15s` before deleting when the tier does not cover
  the window. Verified: 2 pruned slots → 59 buckets in the pruned window, i.e.
  nothing lost.
- byte cap evicts **oldest data first**, by the newest sample in the file, not by
  file name (a name sort put `T04-45` before `T04`, which would have evicted the
  newer slot). Verified on a fixture built to hit exactly that ordering.
- the current 15 min raw slot and the current day's tier file are never rewritten
  or pruned, so a `--compact` run next to a live collector cannot truncate a live
  file.
- every rewrite is `.tmp` → `fsync` → `rename` → `fsync(dir)`; a source file is
  unlinked only after the destination's `fsync` returned, so the worst crash
  leaves one duplicate bucket, deduped by `(bucket_start, tier)`.
- the log root also retains a day link after a demotion, so the dashboard never
  sees a day disappear.
